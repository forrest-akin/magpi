# Handoff: plan the redo of `main`

`7fdb4fa` was built before the user's methodology was loaded. It holds ten port interfaces, the zod
schemas for every on-disk artifact and the work-unit model, none with a caller. They follow the
old plan's bottom-up sequence (`.claude/plans/2026-06-07-workflow-layer/README.md`: ports, fakes,
all adapters, the pure core, commands last). The user chose to redo the code top-down and rewrite
`main`'s history. Write the plan to `.claude/plans/2026-10-26-redo-main.md`.

## Decided

- **Rewrite `main`.** `6f074da` and `8953b17` hold no code and stay as they are; the new history
  branches from `8953b17` on a local branch. `main` moves to its tip only after the tip passes in a
  clean worktree. The force push to `origin/main` waits for the user's explicit approval at that
  moment; no agent pushes.
- **Keep:** `docs/`, `.claude/brainstorms/`, `.claude/skills/`, `.claude/handoffs/`, `CLAUDE.md`,
  `README.md`, `mise.toml`, `.gitignore`, and the findings in `efcb63e` and
  `test/_evidence/gate-bun-pi-go-no-go.json`. Each is replayed onto the new branch and rewritten
  wherever it describes code its commit doesn't have yet.
- **Redo:** `package.json`, `bun.lock`, `tsconfig.json`, `biome.json`, `src/`, `test/`, top-down
  from magpi's entrypoint (the Pi extension module, spec §12), starting with the first vertical
  slice a user can run. Each port, adapter, schema, core function and dependency is built when
  that slice first calls it. Build config carries over only where nothing in it is ahead of its
  first use.
- **The old code and the old plan are sources of findings.** The old plan's task specs remain the
  requirement inventory; its commit sequence is superseded, and its README says so. Whatever the
  old code decided that the spec and ADRs don't pin goes into the plan, in the commit where it
  first applies.
- **The old plan's verification infrastructure** (Tasks 6, 32–35: fakes for every port, fitness
  test, property suite, record/replay, evidence records, `verify` scans) is built only where a
  commit's test needs it. The rest is a proposal for the user, each with the failure it guards.

## The plan contains

1. The replay of kept commits onto `8953b17`: each commit's subject and what its rewritten content
   says, and which checks exist on it.
2. The commit sequence through the first vertical slice. Per commit: Conventional Commit subject;
   the failing test that drives it and why it fails; what it adds; the docs it makes true; the
   checks that verify it. Each commit deploys alone.
3. Later slices as an ordered list of user-visible behaviors, one line each with the spec sections
   it satisfies. Internal seams are left to the loop.
4. The error model for the modules the first slice creates, settled before their code.
5. What needs a spike or a decision record first. The go/no-go probe covered Pi imports and
   `SessionManager` transcript capture; anything else the slice relies on in Pi 0.80.7 is
   unverified until checked against `node_modules/@earendil-works/pi-coding-agent`.
6. The cutover: moving `main`, the clean-worktree check at the tip, and the force push left to the
   user.
7. User decisions, each with options, trade-offs and a recommendation first.

## Constraints

- This phase writes only the plan and checkpoint files under `.claude/work/redo-main/`. No source
  edits, branches, commits or pushes.
- Leave the untracked `.claude/plans/2026-06-07-workflow-layer/handoff-commit-1.md` in place; read
  it for findings.
