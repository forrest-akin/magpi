## 2. Commit sequence through the first slice

The slice: in a git repo, a user runs `pi -e <magpi>`, types `/shape --branch <branch>`, and
magpi checks the branch out, records a work unit in `.magpi/work/<slug>/work.json`, and moves the
conversation into a session whose transcript Pi writes to `.magpi/work/<slug>/sessions/`.
`/shape` again on that branch reports or resumes it.

Layout the slice creates (seams below these are the loop's to find):

```
src/extension.ts          default export: registers /shape
src/shape/command.ts      handler: the shell for /shape
src/shape/args.ts         parseShapeArgs (pure)
src/shape/outcome.ts      outcome union + render to {message, level} (pure)
src/workunit/slug.ts      slugFromBranch (pure)
src/workunit/record.ts    record type, newWorkUnit, startShaping (pure); schema + parse from C3
src/parse.ts              parserFor, ParseError: zod schema to Result (pure, C3)
src/workunit/store.ts     .magpi/work/<slug>/ reads and writes (node:fs/promises)
src/git.ts                repoRoot, checkout, currentBranch (node:child_process execFile, no shell)
```

`.magpi/` lives at `git rev-parse --show-toplevel`, not `ctx.cwd`: the work unit is bound to a
repository branch (spec Non-Goal 4), so two subdirectories must not hold separate folders for one
branch. The handler types `ctx` and `pi` as structural subsets of `ExtensionCommandContext` and
`ExtensionAPI` naming only the members magpi calls, so tests pass plain objects. Tests touch git
and the file system for real, in temp dirs under `os.tmpdir()`; only Pi's `pi`/`ctx` are faked,
because pi cannot run inside `bun test`. Each test builds expected paths from
`fs.realpath(tempDir)`: on macOS `os.tmpdir()` is under `/var` while `git rev-parse
--show-toplevel` reports `/private/var` (checked 2026-10-26).

## 3. Later slices

Ordered user-visible behaviors; internal seams are left to the loop.

1. `/shape` with no args starts an explore session; `/define` derives the slug from the explore
   summary, creates the branch and the work unit. Spec §3 default, §7, Error Handling 5 and 6.
2. `/define` writes the `explore-to-define` brief and starts define seeded with it, injected once
   per session; `session_shutdown` retries a failed `work.json` write once. §1 brief, §7, §10, §12
   `session_shutdown` / `before_agent_start`, Error Handling 4 (its "exits with code 1" is
   rewritten: magpi has no process of its own).
3. `/plan` runs the autonomous plan sub-phase, writes `plan.md`, state `plan-pending-gate`. §1, §2, §7.
4. Gate 1: `/craft` accepts the plan; rejection with feedback retries up to twice, then returns to
   define. §4, SC #5.
5. `/craft` runs autonomous craft with a git checkpoint; a clean exit reaches `awaiting-reflect`. §2, §5.
6. A failed craft past its retry budget is `blocked` with a reason; `/craft` after a kill resumes
   at the checkpoint. §5, SC #3, Error Handling 2.
7. `/shape --abandon <slug>` and closing an `awaiting-reflect` unit. §2.
8. Every command warns when the current branch has no work unit or a `crafting` unit sits on

## 4. Error model for the first slice

The `functional-error-handling` skill's convention, applied:

- Pure functions return `Result` or `Maybe` (true-myth). They never throw for an input they can see.
- IO functions in `git.ts` and `store.ts`, and the handler's call to `switchSession`, return
  `Task<T, ShapeFailure>` built with `task.tryOrElse` (`notify` is a direct call), so no promise magpi awaits rejects. Each
  `onError` maps the rejections it recognizes to a variant below and any other to `Unexpected`.
- `ShapeFailure` is `ShapeError | Unexpected`. `Unexpected {operation, cause}` covers git missing
  or failing to spawn, read errors other than `ENOENT` (`EACCES` included), a session file Pi
  rejects, and any exception from pi's API.
- The handler chains with `andThen`, awaits once, and matches. An outcome or a `ShapeError` is
  rendered and passed to `notify`. On a session switch (C4, C5) the chain ends at
  `switchSession`, and `withSession` awaits and matches a second time: the `work.json` write and
  the notice go through the `withSession` ctx, as the command's ctx throws after the switch.
  `writeWorkUnit` maps every rejection to `WriteFailed`, so `withSession` never throws. An
  `Unexpected` is thrown as
  ``new Error(`/shape: ${operation}: ${causeMessage}`, {cause})``; pi reports only the message, so
  it carries the cause's. That throw is magpi's only one; magpi writes no `try`/`catch`, as
  rejections land in the `onError` mappers.

`ShapeError` is one union tagged by `kind`, matched exhaustively in `render`:

| Variant | Fields | Produced by | Commit |
|---|---|---|---|
| `Usage` | `input` | the handler (C1), then `parseShapeArgs` (C2) | C1 |
| `InvalidSlug` | `branch` | `slugFromBranch` | C2 |
| `NotARepository` | `cwd` | `repoRoot` | C2 |
| `CheckoutFailed` | `branch`, `stderr` | `checkout` (non-zero git exit) | C2 |
| `AlreadyExists` | `slug` | `createWorkUnit`; from C3 only when `work.json` appears after the lookup | C2 |
| `WriteFailed` | `path`, `code` (errno) | any rejection in `createWorkUnit` (C2), `writeWorkUnit` (C4) | C2 |
| `Corrupt` | `path`, `detail` (first schema issue as `<field>: <message>`, `<message>` for a root issue, or the `SyntaxError` message) | `readWorkUnit` | C3 |
| `SlugTaken` | `slug` (the suffixed one), `branch` (its unit's) | handler, when `<slug>` and `<slug>-<crc>` both hold another branch's unit | C3 |
| `Orphaned` | `path` (the unit folder) | handler, when `readWorkUnit` finds the folder without `work.json` | C3 |
| `SwitchCancelled` | `slug` | handler, from `switchSession` | C4 |

`WriteFailed` is expected because spec Error Handling 4 defines its handling (disk full,
permissions); this commits every caller of a write to handle it. A read's `EACCES` has no spec
rule, so it stays `Unexpected`.

**ADR 0003 `magpi runs inside pi's Node process`** (C1). Decision: magpi ships as a
pi package loaded by `pi -e` or settings and runs only inside pi; the extension is the only writer
of `work.json`, with no outer process and no IPC; runtime code uses `node:` built-ins; Pi core packages
are peers; Bun is the package manager, test runner and script runner. Named downside: tests run
on Bun while magpi runs on Node in pi, so a Bun-only behavior can pass the tests and fail in pi;
the manual pi checks in C1-C5 cover the slice. Rejected: a harness process
spawning pi per phase and taking state changes over IPC (spec §2 as first written);
`Bun.$`/`Bun.file` adapters (undefined in pi's Node); bundling Pi (Pi `docs/packages.md` forbids
it).

No new spec: the spec stands, with the per-commit edits above.
